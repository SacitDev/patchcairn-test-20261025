# Workflow service integration

`WorkflowService(engine=None, *, work_relative="work/services")` connects the deterministic conversation engine to fixed storage, diagnostic and package-update adapters. Every toolkit-generated record remains under the executing repository's `work/`; a backup may instead go to a folder the owner chose on another drive. Fixture mutations are restricted to explicitly selected owned fixture children. This service is a trusted coordinator boundary in a quiet workspace, not an OS sandbox against another process running with the same privileges. Schema, backend and adapter identifiers below are unversioned names of internal formats within the single PatchCairn workflow.

The public methods are `prepare_storage_action`, `prepare_diagnostic_action`, `collect_inventory`, `discover_packages`, `prepare_package_action`, `register_recovery`, `protected_roots`, `retention_rows`, `retention_plan`, `execute_action`, `run_ticket`, `ticket_command`, `complete_diagnostic`, `inspect_operation`, `reconcile_operation` and `session_report`. Preparation registers exact immutable adapter/inventory bytes and returns the concrete action specification for an engine plan. It never approves that plan. Execution rechecks the exact registered adapter payload, lower-level plan, source inventory, scope, mode, output and protection policy before consuming an engine operation ticket. No change to files or software begins while the process runs with administrator or root rights.

Storage dispatch uses only `storage.backup_create`, `storage.restore`, `storage.quarantine`, `storage.quarantine_restore`, `storage.purge`, `storage.retention_release`, `storage.session_release` and `storage.retention_forget`; `storage.remove_originals` and `storage.delete_selected` are registered but hold in this version. Diagnostic dispatch uses only `diagnostic.collect` with the fixed recipe IDs documented in [the diagnostic API](DIAGNOSTIC_API.md). Updates and repairs use `package.upgrade`, `package.reinstall` and `system.repair` through the built package routes; `system.update_handoff` (Windows Update, macOS Software Update) and `system.firmware_update` hold. No payload chooses a Python method, shell, executable path or fallback command.

A package step runs in two parts: `execute_action` begins the operation and writes a one-use ticket, and `run_ticket` (the launcher command `patchcairn_service.py run --ticket <ticket>`) checks everything again and starts exactly the bound command. The engine operation stays open until the service records the actual result from fresh reads. Success is never synthesized from writing a ticket or reading a stored plan.

## Normal coordination

1. Create a fresh engine session with its immutable fixture/real mode and native platform. Select exact roots and obtain the owner's actual scope decision using `authorize_scope`. A Python object, quote copied from a file, or imported `approved` flag does not establish human authority.
2. Obtain any separate content-read decision before the storage library hashes selected ordinary files. Build the lower-level native plan using the [storage API](STORAGE_BACKUP_API.md), select a [fixed diagnostic recipe](DIAGNOSTIC_API.md), or read a package manager's offers with `discover_packages`. Keep backup/output destinations and protection policy exact.
3. Call the corresponding preparation method. It registers canonical inventory and adapter payload bytes in the engine and returns an action with exact payload, lower-plan and inventory SHA-256 bindings. It performs no maintenance effect. Preparation still needs the current authorized collection scope.
4. Register a concrete engine plan containing the returned action. Complete the job's evidence stages, two independent reviews, the actual owner plan/action decision (and, for a permanent deletion or firmware update, the typed reply), and selected checkpoints. The service never fabricates those decisions.
5. Register fresh exact-action preconditions. `execute_action` first rejects paused/stopped/non-apply/checkpoint states, revalidates actual owned payload bytes and native freshness, then calls `begin_operation`. Only the resulting one-use durable operation permits a fixed library call or a package ticket.
6. The service persists the complete original payload, action, mode/platform, scope, settings revision and operation binding before the first effect. The original intent is also registered as engine-owned evidence with its exact hash. The engine's last admission (`admit_effect`) comes right before the effect, so a pause or stop either stops the effect there or arrives after it. Quarantine stores its ordered original-file-to-numbered-destination mapping before a move. Native storage attempts separately preserve their complete exact plan.
7. Actual fixed-adapter outcomes are verified from native artifacts or fresh manager reads and registered as owned evidence before `finish_operation`. Verification of the original application behavior and any security remediation remains a separate engine stage. An exit status or matching version is not whole-system verification.

The coordinator writes service and engine state sequentially. The service uses an operating-system file lock, exclusive immutable files and flushed writes; the lock ends with the process that held it. A missing creation marker, changed intent/evidence hash, missing native receipt or unsupported capability is a hold. Generated evidence is private and is never part of the public website or published source.

The dedicated service, operation and diagnostic namespaces use the common `private_workspace.py` admission boundary before private writes. New Windows directories have an actual verified current-owner/SYSTEM/Administrators-only protected DACL; new private files receive and verify an explicit descriptor before payload bytes. POSIX requires actual effective-user ownership and `0700` directories/`0600` files plus the native platform checks below. Service control reads recheck file privacy. Existing broad namespaces are refused without ACL/mode repair, while the ordinary repository and `work/` ancestors may remain shared. The storage library separately requires a private output namespace for its control records, probe and copied contents.

Linux additionally checks the actual filesystem using pinned ordinary descriptors and read-only `fstatfs` before allocation and private-object use. The reviewed x86-64 LP64 little-endian glibc 2.x ABI admits ext2/3/4, XFS, Btrfs, tmpfs and ramfs; unknown ABIs/types, network/FUSE and Windows-mounted or NTFS-emulated storage hold even if reported modes appear private. Native ext4 under WSL can satisfy the type gate; a Windows-mounted path such as `/mnt/c` is refused before private bytes. Mocked positive filesystem tests are not an actual ext4 host certification.

Darwin additionally requires the source-verified read-only volume gate: reviewed writable local APFS/HFS+ with ownership enforced, using the fixed 64-bit x86-64/arm64 ABI. Ignored ownership, FSKit, unsupported volume types/ABIs and query errors hold. The native ACL checker must also establish a valid empty extended ACL or the precise source-verified absent-ACL result, with stable ordinary identity. Nonempty ACLs, unavailable APIs, unexpected results or changed identities hold; BSD mode alone is insufficient. The hosted macOS CI job runs the private-storage, archive/probe/record and integrated service fixtures through these gates; see [platform evidence](PLATFORM_SUPPORT.md#hosted-fixture-evidence). Unsupported volume/ACL states and other ABI/filesystem variants retain their separate limits. No alternate public directory or silent permission repair is used. Old broadly accessible data remains unchanged and needs its own reviewed containment decision; nothing erases or silently migrates it. The [diagnostic API](DIAGNOSTIC_API.md) describes these shared platform boundaries and primary permission-model references.

## Public Python interface

Import `WorkflowService` and `ServiceRefusal` from `scripts/workflow_service.py`. Use an existing supported Python 3.12+ installation. The default engine and service root come from their scripts. New default namespaces are `work/sessions` for the engine and `work/services` for the service, with its diagnostics below `work/services/diagnostics` and package run folders below `work/package-runs`. Development root overrides must remain below the executing repository's `work/`. An explicit valid work-relative path selects only that store; no old namespace is discovered, adopted, migrated or deleted when these defaults are used.

The preparation methods take `session_id` plus keyword arguments for the action's reviewed nonsecret text (`target`, `benefit`, `risk`, `reversibility`, `verification`); the storage and diagnostic methods also take `action_id`. They return engine action specifications with bound owned evidence IDs; they do not register or approve the enclosing plan.

| Method | Additional keyword arguments and result |
| --- | --- |
| `prepare_storage_action` | `action_id`, `adapter_id`, `storage_plan`, `output_root`, optional `protected_roots`, `recovery_evidence_ids`, `requires_os_consent=False`, `restore_probe_destination=None`, `backup_destination=None`. Calls the library's read-only native precondition checker, then registers the exact payload. A permanent deletion's payload carries the number of items and bytes its plan deletes, which the typed reply names. A backup to a chosen drive carries `backup_destination`, which also becomes a protected root. Source roots must equal the engine's authorized scope. |
| `prepare_diagnostic_action` | `action_id`, `recipe_id`, `symptom`, `diagnostic_scope`. Creates an immutable bounded diagnostic request in the same mode/platform and binds that request as the selected target inventory. |
| `collect_inventory` | Optional `collector` (tests only). Runs the session platform's installed-software collector in a real session with authorized scope and registers its result as inventory evidence. A practice session is refused. |
| `discover_packages` | `manager`, optional `other_apps=False`. Reads one manager's offered updates through fixed read-only commands in a fresh private run folder and registers them, with the age of the package lists, as inventory evidence. It changes no installed software (the manager may refresh its own lists). A practice session is refused. |
| `prepare_package_action` | `adapter_id`, `items` (one to 500 selected packages, each with its `action_id`), plus the reviewed text. Reads each item fresh and binds its exact id, version, source, preflight result and executable, in one dependency-preserving order; returns one action per package. A practice session is refused. |
| `protected_roots()` | Returns the mandatory current engine/service evidence and retained-recovery directory boundaries. Include these when planning lower-level storage inventories; the service combines them with explicit custom protections in the reviewed payload. |
| `register_recovery` | `output_root`, `backup_receipt`, `restore_receipt`. Verifies actual native archive/manifest/probe bytes and their gated same-mode origins, registers exact engine retention/recovery evidence and protects the retained output. Returns the engine recovery evidence row. |
| `retention_rows()`, `retention_plan(adapter_id, *, names=None, session_id=None)` | The kept backups and recovery records with their sizes, and the storage plan that deletes chosen kept items (`storage.retention_release`), all kept items of one finished session (`storage.session_release`), or forgets items already deleted outside PatchCairn (`storage.retention_forget`). |
| `execute_action` | `action_id`, `plan_sha256`, `precondition_evidence_ids`, optional `diagnostic_fixture_runner`, `diagnostic_fixture_result`. Runs one fixed storage or diagnostic adapter after the exact gate, or, for a package action, begins the operation and returns its ticket and launcher command. Fixture injection is forbidden in real mode. |
| `run_ticket` | `ticket_id`. Runs one ticket once (see below). |
| `ticket_command` | `session_id`, `operation_id`. The launcher command of that operation's ticket, which the check after a restart runs again; `None` when it has no ticket. |
| `inspect_operation` | `operation_id`. Read-only original intent, current engine operation and effect-boundary state. Verifies the full intent against engine-owned bytes before returning it. A step cut off before its intent was written is reported as such. |
| `reconcile_operation` | `operation_id`. Reopens only the exact stored native outcome, or reads a package step's result again, and rechecks real postconditions. A missing/inconsistent outcome remains unknown and consumed. It does not retry an action. |
| `complete_diagnostic` | `operation_id`, `adapter_result`, `coordinator_observed=False`. Accepts only a trusted coordinator's observation for the active matching diagnostic operation and validates the fixed adapter schema and request/mode/platform before persistence. |
| `session_report` | `session_id`. Writes the HTML view of one session as a new private file under the service's `reports` folder and returns its path. It is rebuilt from the session record each time and never read back as input. |

Storage preparation binds this payload, including the constructor's protection policy:

```text
schema: patchcairn.storage.adapter
schema_version: 1
operation: one of the fixed storage adapter IDs
storage_plan: complete original native plan
storage_plan_sha256: actual canonical lower-plan SHA-256
output_root: exact existing owned work directory
mode: immutable session fixture/real mode
protected_roots: exact mandatory and explicitly selected protection boundaries
backup_destination: optional chosen folder on another drive, backup_create only
restore_probe_destination: optional exact new output child, backup_create only
delete_count, delete_bytes: what a permanent deletion removes, deletions only
```

`storage.backup_create` maps only to `create_backup`, `storage.restore` only to `restore_backup`, `storage.quarantine` only to `quarantine`, `storage.quarantine_restore` only to `restore_quarantine`, and `storage.purge` only to `purge_quarantine`; the three retention adapters run the service's own release or forget of exact registry rows. There is no dispatch through an imported Python method name. Lower-level plans keep their actual kinds `backup`, `restore`, `quarantine`, `quarantine_restore`, `purge`, `retention_release`, `session_release` and `retention_forget`. Native preconditions are checked again at the effect boundary by the storage library.

## Recovery and irreversible loss

Required recovery uses actual ZIP/manifest hashes, exact member mapping and bounded contents, native artifact identities, a completed restoration probe and every probe file's verified bytes. Engine recovery validation reopens those artifacts; `verified: true` facts or a supplied JSON receipt alone do not establish recovery. Service native-origin records bind the archive/probe to the same engine and fixture/real platform. Retention records preserve all exact artifact hashes and conservatively protect their output directories from later host-cleanup scope. Kept files are deleted only through a reviewed retention release; there is no automatic expiry.

A required backup may be protected before its archive is complete. Incomplete or unknown artifacts remain protected because an interrupted operation is not proof that no useful recovery data exists. The service protects existing evidence and required recovery across later sessions that use this service. A kept backup on a drive that is not connected is checked by its recorded text only until the drive is back. The service does not discover or claim authority over every backup elsewhere on the computer.

Every integrated quarantine also reserves its exact output namespace before the first move, including quarantines that do not require a ZIP. A typed retention record binds the complete original native plan, ordered original-to-numbered-file mapping, original intent/native provenance hashes and expected or pending native artifacts. The reservation survives completed, stopped, partial and unknown outcomes. Later sessions include that namespace in their protection policy; overlapping output/source plans are held. Only restoration or backed purge of the exact original receipt and mapping can operate on that reserved quarantine. There is no automatic release.

For an initial backup's verification, the reviewed `backup_create` payload can include an exact `restore_probe_destination`. This is a bounded substep of that same approved action: create/verify the selected archive, derive its exact restore mapping from the verified manifest, persist the complete derived native restore plan before writing, restore only to the reviewed new owned destination, and verify actual bytes. It does not overwrite original files. This supplies actual probe evidence without requiring a previously completed probe to authorize the first probe. A probe is refused before the backup begins when the backup could exceed the restore's 32 MiB archive or 16 MiB file limit; the backup can then be planned without it. A verified backup whose probe did not finish reconciles as partial.

These ZIPs preserve selected file contents; they are not encrypted system images and do not promise application, OS, ACL or firmware rollback. The assistant must explain recovery limits for the actual repair/update. A repair whose required recovery cannot be established remains held.

In particular, a verified ZIP of a small file in the authorized scope cannot satisfy recovery for Windows component-store or Linux package-state repair. Finishing an interrupted dpkg setup (`system.repair`) has no component rollback and needs the owner's separate acknowledgment of that (`record_irreversible_ack`); file-content recovery is never presented as OS rollback. Diagnosis, selected evidence and official research can continue; the missing recovery capability and practical next decision must remain explicit.

A backup streams its files and holds at most 100,000 of them; its destination needs free space for the archive's worst-case size plus a 256 MiB margin, and a FAT32 drive refuses a backup that can reach 4 GiB. Quarantine and duplicate comparison read at most 16 MiB per file and 48 MiB in total, and the restore reads at most a 32 MiB archive and 16 MiB per file. These practical caps are not a whole-computer backup service. Disk cost, duration and actual reclaimable space remain unknown where they have not been measured.

Restoring an existing quarantine has a narrower recovery guarantee: its actual bytes already remain in the numbered quarantine. `prepare_storage_action` for `storage.quarantine_restore` creates `patchcairn.quarantine.recovery` evidence containing the exact immutable quarantine receipt, exact restore plan/hash and retained current files/attempt/outcome hashes. The engine accepts that proof only for the same quarantine-restore adapter and native plan hash. Native checks reopen the original immutable provenance, verify every identity/content/mapping and require absent original destinations and a checked no-overwrite move. This supports restoration of an explicitly reviewed quarantine created without a separate ZIP; an unrelated backup is not required or accepted as a substitute. The typed quarantine binding cannot satisfy repair, permanent purge or generic backup restoration recovery.

Permanent purge is a separate plan/action from quarantine. After both reviews, the engine's `issue_irreversible_warning` records the warning with the number of files and bytes and its exact phrase (for example "delete 12 files"); `approve_plan` accepts the plan only when the owner's own message is that phrase, so one message is both the approval and the acknowledgment. The record shows that the engine received the phrase, not who typed it: it catches a reused or mismatched reply, not a forged one. A boolean in an imported payload or a previous quarantine approval cannot satisfy it. Integrated purge is held when the original quarantine did not require recovery. For a backed quarantine, the accepted engine recovery must match that original receipt's exact backup, restoration probe, output root and covered file mapping; a valid backup of another selection cannot substitute. The service still checks exact current quarantine provenance/content and retained recovery before individual no-fallback removals. Deleting kept backups (`storage.retention_release`, `storage.session_release`) uses the same typed reply, with the phrase "delete N backups".

## Package update and repair routes

The built routes are winget (Windows, run without a terminal), Homebrew (macOS, run without a terminal), and apt and dnf (Linux, run in the owner's own Terminal through sudo). Each route reads its manager through fixed read-only commands, and every argument it may pass is an allowed row of a reviewed token table that cites the manager's official documentation. Updates bind the exact package id, version, source and the manager's own dependency data; a repair is a same-version reinstall (Homebrew, apt) or finishing an interrupted package setup (apt, through dpkg). DISM repair holds because its exit codes are not documented and not captured; System File Checker and winget repair are guidance only. Python packages, Node packages, Windows Update, macOS Software Update and firmware have no built route in this version.

`run_ticket` runs one ticket once. It refuses while PatchCairn has administrator rights, or when that cannot be told. It reads the session and the operation's checked intent again and refuses an operation that is no longer open or already started. It then reads the exact approved binding again with its freshness limit, hashes the run files again, checks the executable again (its record names where it is: the winget App Installer package folder, the Homebrew prefix or the root-owned system path; it binds the location, not the file's content), requires a terminal on stdin and stdout for a terminal route (otherwise nothing starts and the launcher command is returned for the owner), runs the route's drift check right before the argument list is built, and finally passes the engine's admission, which refuses a pause or stop that arrived meanwhile. It starts exactly the bound executable with the bound arguments and environment, without a shell, and records the child's exit as soon as it is known. It never kills the child, never restarts the computer and never runs a command it is handed. An item that the manager no longer offers because an earlier step already brought it to its approved target starts nothing.

Each result is classified from fresh reads before and after the run (update result codes such as `updated`, `restart_needed`, `did_not_update` and `could_not_check`), and the operating-system consent is recorded after the run from what was observed: for sudo, exit 0 means that sudo ran the command, not that a person typed a password, because a recent sudo use or a NOPASSWD rule shows no prompt. A package's scripts, dependency/state effects and restart needs still need review and actual verification. A separately approved real installation can create native OS/package records outside `work/`; those are not toolkit cleanup targets.

When a route reports that a restart is needed (a reboot-required file, a manager's restart check, the Windows reboot-pending keys or an installer's exit code), the engine's `record_restart_pending` keeps the step open in the restart class: it is not run again and only a backup can start. A signal read again from the same place can clear it; a signal from an exit code ends only with a restart. After the owner restarts, the check after the restart runs the same launcher command (`ticket_command`, also printed by `patchcairn_service.py inspect-operation`): `record_boot_observation` records a boot later than the step and every reading of its signal, and the step's result is then read and recorded once. A stopped session keeps this check for its open step; it gains no new plan, action or ticket. PatchCairn never restarts the computer.

The relevant primary references are cited per token in `scripts/package_tokens.py`; their commands describe capabilities, not authority to run them.

## Pause, stop and interrupted operations

Pause/stop blocks new dispatcher work before native precondition collection or a new operation begins. An already active effect reaches its safe receipt checkpoint; the helper does not kill an installer, force-close an application or resume a paused session. If the owner pauses/stops after the operation begins but before the first adapter effect, the engine's admission refuses the effect and the service finishes the step as failed, recording that no adapter was invoked.

The engine accepts the late exact outcome of an already active operation after stop. The service preserves stopped/paused status when recording it; success does not silently resume the workflow. Changing scope/settings during an active operation is refused. Later material changes invalidate old plan/review/approval bindings. Selected checkpoints remain the engine's explicit current-owner decisions.

If a native call raises after entering its effect boundary, a file may already have moved or been written before its step receipt. The service records a categorical unknown with possible partial effects and retains the original full intent, ordered mappings, native attempt/step/outcome records and required recovery. It excludes raw exception text. No automatic retry occurs, even when a final outcome file is missing. A step that was cut off before its intent was written started nothing; inspecting or reconciling it closes it as not run.

`reconcile_operation` can establish success only by reopening the exact immutable native outcome and verifying actual archive/restored/quarantined/purged state through the storage library, or by reading a package step's result again. Native outcome and probe-outcome files must pass private-file admission before their content is read. A fresh real observation can resolve an earlier unknown through the engine while preserving history. Absent, privacy-refused or inconsistent native outcomes remain unknown and consumed; a package step without a recorded exit stays unknown, so a child that outlived its parent is not reported as finished. The service never manufactures an outcome because time passed or a process disappeared.

Old receipts cannot acquire a new scope or settings revision. Completion and reconciliation require the original intent's exact scope, settings revision and immutable operation binding to match the current session; reconciliation checks this before native artifacts are opened, and completion checks fresh state again before writing or registering an outcome. A mismatch is held without relabeling, migration or retry. Read-only inspection can still show the original historical intent. Pause/stop and ordinary event-revision changes under the same scope/settings authority still permit actual late outcome accounting.

## Read-only terminal surface

`scripts/patchcairn_service.py` exposes `catalog`, `status SESSION_ID`, `inspect-operation SESSION_ID OPERATION_ID`, `report SESSION_ID`, `retention` and `run --ticket TICKET`, with optional internal `--json`. It starts only as `python -I -S -B`; any other start is refused before anything is written. It accepts named work-relative engine/service storage only. `inspect-operation` prints the command of the check after a restart when the step waits for one. `run --ticket` runs exactly one approved, reviewed package step; there is no CLI operation that imports and executes a JSON action, approves a plan, creates a host schedule, purges files or runs a shell command. Use the coordinating assistant and the actual engine/library APIs for reviewed work.

## Validation evidence and limits

The included [service tests](../tests/test_service_execute.py), [diagnostic tests](../tests/test_diagnostic_core.py) and platform privacy tests provide reproducible fixture entrypoints; the repository's current CI selects supported platform groups. They use selected synthetic ordinary files, actual checked filesystem/archive operations where the host supports them, fictional owner/review decisions, mocked POSIX diagnostic output and fictional package-manager output. No test inventories the computer, reads real logs, installs software or performs a live repair. Native OS command behavior is not inferred from fixture results.

There are separate native Windows tests for owner-private namespace/file admission and refusal of preexisting broad namespaces before markers or payloads, plus actual mounted-filesystem refusal tests. A private-mode guard is not represented as a passing functional run on an unsupported mounted filesystem.

The suites check mismatched approved/actual plans, wrong root/output/type/hash, content and precondition freshness, reused tickets, pause/settings/stop/checkpoint boundaries, late outcome evidence, exact protected recovery, the typed reply for permanent deletion, diagnostic fixture isolation, and interruptions after a real fixture write/move. A mounted filesystem that cannot provide native no-overwrite moves must hold that success path; it must not use a copy/delete fallback. Actual host results and capability skips remain part of the evidence; see [the hosted fixture record](PLATFORM_SUPPORT.md#hosted-fixture-evidence). Diagnostic and package-manager contracts remain injected or fictional, and broader native support is not inferred.
