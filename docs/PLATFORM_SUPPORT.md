# Requirements, platform implementation and validation

This reference separates available implementation from actual test evidence. Windows, Linux, and macOS have platform-specific code and shared skills; that does not establish equal native validation or make every update/repair route available. The README introduces the skillset; this file supports capability checks and accurate operating decisions.

For the source-download, extraction, and local-assistant steps on each OS, use [getting started](GETTING_STARTED.md#1-download-and-extract-the-source). Start with the menu in the assistant's chat. No computer information is collected until the owner chooses a job and authorizes the selected assessment scope. `PatchCairn:` requests are chat instructions, not operating-system shell commands.

## What the project provides

PatchCairn is a reusable instruction/skill set plus local scripts. The AI assistant conducts the investigation and coordinates supported official tools within the exact documented contracts and owner authority. The conversation workflow provides durable conversation state, bounded selected-file storage/backup services, package update routes, fixed diagnostic recipes and an HTML session report. Opening the project does not start an installer or a background maintenance service.

Use an assistant with project-file access, a suitable shell and current web research. Check its actual privileges and available tools. Use the host's computer-use skill only when GUI interaction is necessary. A missing capability is explained before the dependent operation.

No extra Python packages are required. The Windows selected-file backend runs inside the Python process: each selected root has its own I/O thread holding its handles, and a native call that does not return in time is cancelled and reported as unresolved. No plan supplies executable code or authority. Missing prerequisites cause a hold, without a weaker fallback, elevation or silent installation. Check an existing runtime's supported source/channel as part of a real assessment.

The supplied CI runs every Python test suite on Windows, Ubuntu and macOS with Python 3.12 and 3.15, the offline JavaScript report fixtures with Node, and the PowerShell suites under PowerShell 7 and 5.1; [GitHub setup](GITHUB_SETUP.md#future-ci-and-publication-metadata) lists the jobs and time limits. A capability skip remains a skip; it does not establish that the skipped native action worked. Treat actual run results and their exact source binding as evidence when available; a checked-in workflow file is not a successful hosted run.

## Hosted fixture evidence

Use the public [fixture-safety workflow](https://github.com/SacitDev/PatchCairn/actions/workflows/ci.yml) to check validation of the published source. Match a completed run to its source commit, runner, runtime and skips before carrying its result to that snapshot. The tested contexts below do not by themselves establish that the published snapshot has passed.

The CI jobs run the fictional fixtures on hosted `windows-latest`, `ubuntu-latest` and `macos-latest` runners. The native tests operate on fictional files inside owned `work/` directories: metadata/hash/bounded reads, exclusive creation, exact deletion, no-overwrite quarantine and restoration, ZIP/manifest creation and restoration, private-file admission and the integrated service flows. Native success tests assert source/destination state and file bytes; unsupported native capability routes skip rather than use a weaker fallback. Separately mocked rename/error contracts remain distinct. The offline report JavaScript fixtures use a minimal fictional DOM; they are not browser/layout tests.

Each runner skips the tests of other platforms, and every skip names the platforms its test runs on. Skips establish no successful action. Runner-image labels do not independently identify exact fixture-volume filesystem types; these results do not certify every APFS/HFS+, Linux filesystem, architecture or OS version.

Diagnostic collector output and package-manager output in the tests are fictional or injected; no test starts a real package manager or installer. No live inventory, diagnostic collection, package installation, repair, restart or whole-system assessment is claimed. Current published-source counts, capability skips and native success assertions must be checked in the matching completed public workflow; an implementation, a workflow definition or a green aggregate label alone is insufficient.

## Capability and evidence boundaries

This page records no test counts. Counts, capability skips and native success assertions for the published source are those of the matching completed run of the [configured workflow](https://github.com/SacitDev/PatchCairn/actions/workflows/ci.yml). Pure and mocked contract tests do not establish native success, and suite completion does not establish general workload speed.

| Capability | Windows | Linux | macOS |
| --- | --- | --- | --- |
| Selected-root metadata and bounded checked reads | Native ordinary-file checks on NTFS through the in-process handle backend. | Descriptor-based checks; a Windows-mounted WSL folder refuses private storage. | Descriptor-based metadata/hash/bounded-read checks. |
| Quarantine and restore | Identity/content-bound, same-drive, no-overwrite handle rename. | `renameat2` with `RENAME_NOREPLACE`; a filesystem without it holds. | `renameatx_np` with `RENAME_EXCL`; mocked call/error and no-weaker-fallback checks remain separate. |
| Exact approved purge | Single-file purge with a name-absence check. No recursive selected-root purge is exposed. | Exact descriptor-relative deletion. No broad recursive cleanup is exposed. | Exact descriptor-relative deletion and separate quarantine purge. No broad recursive cleanup is exposed. |
| Backup and restoration verification | Streamed ZIP/manifest backup through the checked selected-file backend, to the work folder or to a chosen fixed or removable drive. | The same through descriptors; an unsupported mount holds its dependent routes. | The same through descriptors. These are bounded fictional file-content fixtures. |
| Fixed diagnostic recipes | Five Windows recipe contracts with injected facts; the PowerShell helper's fixture mode is tested on its own. No live collector runs. | Kernel-version/root-capacity recipes with mocked runners. No live collector runs. | OS-version/Data-volume capacity recipes with mocked runners. No live collector runs. |
| Workflow approvals and receipts | Shared deterministic workflow/state fixtures are separate from native outcome verification. | The same distinction applies; a state transition cannot stand in for a missing native capability. | The same distinction applies; a modeled Darwin call cannot stand in for actual native execution. |
| Package update route | winget, run without a terminal. | apt and dnf, run in the owner's Terminal. | Homebrew, run without a terminal. Tests use fictional manager output only. |

An update step runs only through its one-use ticket: the launcher checks the binding and the manager's current offer again, starts exactly the bound command without a shell, and refuses to run while PatchCairn has administrator rights. The result is read from the manager afterward. Windows Update, macOS Software Update, firmware, and Python and Node packages have no built route, and PatchCairn does not repair Windows itself. A verified file-content ZIP is not OS rollback or package-state recovery. Fixture contract validation does not claim that any installation occurred.

A step whose route reports that a restart is needed stays open: it is not run again, and only a backup can start meanwhile. No helper restarts the computer. The check after the restart records a boot later than the step, then reads the result; a signal that came from an installer's exit code ends only with a restart. These implemented contracts and fictional receipts do not establish that a live installer or restart has run. See [service integration](SERVICE_INTEGRATION.md).

Metadata assessment and content reading have separate budgets. Duplicate comparison and quarantine read at most 16 MiB per file and 48 MiB in total; a backup streams up to 100,000 files; PatchCairn's own restore reads archives of at most 32 MiB and files of at most 16 MiB. Metadata totals do not silently remove oversized files from an assessment. For larger selections, propose a separately reviewed suitable backup route with exact contents, exclusions, destination and restoration verification. Never trim required recovery silently or claim ZIP compression provides encryption.

## Operating limits

### Private storage is a prerequisite

Before persisting selected evidence, the current workflow, service, diagnostic and backup code verify their private namespaces. A shared repository or ordinary `work/` ancestor is different from a private record store. Existing unsafe stores are held without changing their permissions or adopting old records.

| Platform | Current private-storage condition |
| --- | --- |
| Windows | New namespaces and records request the current token user's ownership and a protected DACL allowing only that user, SYSTEM and Administrators. Actual ownership and access rules are checked before private bytes. The private folder must be on a local drive (no network path), its full path at most 240 characters, and every folder name in it one PatchCairn accepts (no reserved Windows name or unsupported character, at most 255 UTF-8 bytes). |
| Linux | Actual effective-user ownership and directory/file modes `0700`/`0600`, plus the reviewed native-filesystem check. The initial checker supports little-endian x86-64 LP64 with glibc 2.x and admits ext2/3/4, XFS, Btrfs, tmpfs and ramfs. Unknown, network, FUSE, NTFS emulation and Windows-mounted/9p storage hold before private writes, even if metadata reports private modes. This permits a supported native Linux filesystem within WSL; it does not certify every WSL mount. |
| macOS | Actual owner/private modes, the native filesystem-admission check, and the separate read-only extended-ACL checker. The filesystem checker supports the source-verified 64-bit little-endian `arm64`/`x86_64` native ABI and admits only writable local APFS or reviewed HFS+ subtypes 0–3 with ownership enforcement enabled. Ignore-ownership, FSKit, read-only/network/unknown filesystems and ambiguous ABI/API results hold before private bytes. ACL admission separately requires a validated empty ACL or its precisely verified absent-ACL state; entries, errors, changed objects and unavailable APIs hold. The native admission runs in the hosted macOS CI job; unsupported volume/ACL states remain separately mocked contract checks. This does not certify all supported filesystem or ABI variants. |

On a Windows-mounted WSL folder such as `/mnt/c`, the gate refuses private record allocation, so the tests that need private storage hold there; the negative capability checks confirm that no private namespace or payload is written on the refused filesystem. Positive Linux filesystem and Darwin native-call variants retain mocked contract coverage. Windows private namespaces and records have actual owner/DACL fixture checks.

The native ABI, ACL and access-control boundaries are detailed in [the filesystem contract](SCOPED_FILESYSTEM.md), [the Windows adapter](WINDOWS_ADAPTER.md), and the source helpers. A capability hold is not authority to weaken permissions, remount a filesystem, change its metadata options, or move fixtures outside the selected workspace to manufacture a pass.

- The collectors gather selected metadata. Current releases, vendor support, advisory applicability and compatibility still require fresh research and reconciliation.
- Keep different installation owners, architectures, project environments and publisher bundles distinct. A system runtime update does not patch every application-owned copy.
- A session's creation backend, mode and platform are immutable. Use a fresh session rather than promoting fictional evidence; records in an older format are refused, never migrated.
- Keep selected scopes and output owner-controlled and quiet on every platform. Windows holds the selected root and its ancestors open for the root's lifetime; POSIX uses checked directory descriptors. Neither provides a multi-operation transaction or an OS sandbox against same-user/privileged concurrent mutation. Avoid shared, synchronized or concurrently modified work folders. Interruption or a failed postcondition requires reconciliation before another action.
- Native no-overwrite rename is capability-gated. A missing symbol, unsupported filesystem, different volume, reparse/symlink, hard link, changed identity/content, inaccessible ancestor or permission barrier is a hold. Do not substitute ordinary overwrite-capable rename, cross-volume copy/delete, force, ACL repair or ownership changes.
- The local v9fs test filesystem did not establish native ACL-denial or actual FIFO-creation behavior. Injected admission checks passed; those limits do not become native ext4/APFS proof.
- Diagnostic requests are data, not proof of owner permission. The coordinator explicitly authorizes a bounded real recipe in the current process. Diagnostic evidence records distinguish observation, hypotheses, cause, confidence, repair and actual verification. No recipe executes a repair or reads arbitrary logs/credentials.
- Protected consent, authentication and separately authorized restarts remain owner interactions. Permissions and host tools, rather than Markdown instructions, enforce OS access boundaries.
