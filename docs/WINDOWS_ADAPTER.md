# Windows selected-file and diagnostic adapters

The storage service uses a dedicated Windows adapter for explicitly selected ordinary files. It can take bounded snapshots and verified reads, create new backup files, move one reviewed file into quarantine or back to its original scope, and purge one explicitly approved file. The coordinator remains responsible for the owner's actual authorization, protected-location policy, recovery requirements and durable operation receipts. Calling a lower-level function is not evidence of consent.

The adapter is `scripts/windows_scoped.py`, which calls Windows through `scripts/win32_files.py` (Python `ctypes` bindings) inside the Python process. There is no separate worker process, PowerShell host or compiled helper for file work.

## First Windows session

The workflow CLI with no arguments, or a bare `PatchCairn: start`, displays the menu without allocating a session or collecting host information. Choosing a job with `--mode real` binds the new session to the detected native platform before private storage is allocated; Windows is detected from the runtime platform identifier, without inventory collection. An explicitly different or unknown real platform, or an unsupported host, is refused before session allocation. Fixture mode remains the safe CLI default and may use `unknown` for pure state tests; explicitly select `--platform windows` for Windows adapter fixtures. Creation mode and platform remain immutable, so a fixture never becomes a real session. Actual scope authorization, protected consent and the exact reviewed plan are still separate requirements.

Use a reasonably short local folder for PatchCairn: every full path the adapter selects or creates stays within 240 UTF-16 units, and a new file's temporary name must fit as well, so files are created only in folders whose full path has at most 198 units. Private records also need a local drive path (no network path) of at most 240 characters, and every folder name in it must be one PatchCairn accepts: no reserved Windows device name, no control or wildcard character (DEL included), no unpaired surrogate, no trailing dot or space, and at most 255 UTF-8 bytes. A menu can display successfully while the first private record holds because its path is too long or a name is refused; the refusal names the folder. Explain the hold before choosing a shorter location for a fresh session; do not silently move, adopt or promote existing records.

## Runtime and native boundary

`scripts/scoped_fs.py` delegates Windows calls to `scripts/windows_scoped.py`. The adapter requires 64-bit Python 3.12 or later on Windows; otherwise it holds with a capability reason. It refuses to run under thread impersonation, and the service starts no change to files or software while the process runs elevated. It takes no executable command, script block or expression from a plan or JSON record. Access controls, antivirus and other OS restrictions remain effective; no bypass or elevation request is supplied.

Before writing private bytes, PatchCairn creates or admits its private folders through `scripts/private_workspace.py`. On Windows it uses the actual current-process token user and native security APIs to create a protected inheritable DACL allowing only that user, SYSTEM and Administrators. It reads back the real owner, DACL, ordinary-file type and persistent-ACL capability. Broad or unsupported existing namespaces cause a hold; it does not change existing ACLs, take ownership or adopt an old permissive directory. Ordinary shared repository/work ancestors may remain shared.

New files that the adapter creates on a private volume receive an explicit creation-time descriptor owned by the process's actual token user, with a protected DACL restricted to that user, SYSTEM and Administrators. The adapter reads back the DACL before the first payload byte and again when the file is committed. This preserves strict current-user admission even when a process token's default owner is an administrator group. It changes no existing owner or ACL and does not require elevation.

This does not make historical artifacts private. An old namespace with broader permissions is refused before anything is written. Its files are not scanned, deleted, moved or repaired automatically; their separate disposition belongs to the owner. SYSTEM, Administrators and the same user remain outside this confidentiality boundary.

On Linux the shared private-artifact helper requires actual effective-user ownership and 0700 directories/0600 single-link ordinary files, plus a read-only native-filesystem gate before allocation and on actual objects before use or payload bytes. The currently reviewed gate supports glibc Linux x86-64 LP64 and allows ext2/3/4, XFS, Btrfs, tmpfs and ramfs. Unknown, foreign, network, FUSE, NTFS and 9p/DrvFS filesystems hold, even if Linux metadata reports 0700/0600. It does not reject WSL categorically: a supported native Linux filesystem can pass. This performs no host-ACL bridge, mount/configuration change or permission repair.

Darwin admission requires actual effective-user ownership and 0700 directories/0600 single-link ordinary files, plus a fixed read-only filesystem check on the existing allocation parent and actual private object. Only reviewed writable local APFS/HFS variants with ownership enforcement enabled can pass; an ignore-ownership volume, unsupported filesystem or native interface, or a query error holds before private payload bytes. The separate extended-ACL checker permits only a source-verified absent ACL property on the same checked object or a valid empty ACL. Any ACL entry or unsupported query state is a hold. These native interfaces and return states have mocked coverage and primary-source review, and the hosted macOS CI job runs the private-storage and file-operation fixtures. The [platform evidence](PLATFORM_SUPPORT.md#hosted-fixture-evidence) describes that context; unsupported states and other filesystem/ABI variants remain outside it. See the [filesystem contract](SCOPED_FILESYSTEM.md) for the exact platform limits.

Selected source roots must be existing folders on a fixed local NTFS drive. A backup destination can be a folder on a fixed or removable NTFS, exFAT or FAT32 drive: only a fixed, non-removable NTFS drive keeps the backup private, so any other drive needs the owner's acknowledgment bound in the approved plan, files there are bound by size and SHA-256 instead of file IDs, and FAT32 refuses a file of 4 GiB or more. The adapter refuses drive roots, UNC/network paths, device and extended-path syntax, paths over its 240-unit bound, alternate data streams, ambiguous or non-canonical components and reserved DOS names. Other filesystems and an unavailable volume capability produce a hold. The same-drive requirement for a move is deliberately stricter than detecting every possible volume alias.

`CreateFileW` opens every ordinary ancestor from the drive root through the selected directory with reparse-point processing disabled; each component below the root is looked up in its parent's index before it is opened, so reparse points and cloud placeholders are refused unopened. Every opened handle is checked against the requested final path, disk-file type and native metadata. The selected root and its ancestors stay open, without delete sharing, for the root's lifetime, so none of them can be renamed or removed meanwhile; a file being read is shared for reading only. Reparse points, files with multiple hard links, offline/recall files and encrypted files are refused. System files are refused for changes, and a read-only file is removed only when the approved plan shows it as read-only and the drive can delete it without changing it. The implementation never takes ownership, changes an ACL, clears protective attributes or enables token privileges.

The adapter compares volume serial, file ID, size, write time, link count and attributes, and requires a fresh SHA-256 match for content operations. Windows records use the volume serial as `device` and the 64-bit file index as `inode`; `mode` is synthesised as `os.stat` does (`0o100666` for a file, `0o100444` for a read-only file, `0o040777` for a directory), and `attributes` are the Windows file attributes without the archive bit and without NORMAL. These fields are adapter-specific and must not be interpreted as POSIX permission bits or POSIX change time.

For a move, the source and destination folders are held together. `SetFileInformationByHandle` renames the actual checked source handle with replacement disabled; it then verifies the destination path, identity and content. There is no cross-volume copy/delete fallback. Restore uses the same operation with the reviewed source and destination reversed. Purge opens the checked file with no sharing, so nothing else can open, change, rename or delete it between the hash and the delete; it marks the handle for deletion and then verifies that the exact name is absent. Pending deletion or a failed postcondition is unresolved, not success. A purge is permanent and requires its separate approval through the coordinator.

`ScopedRoot` binds the selected root's identity across calls through its open handles; it is not a lock on the files inside it. Snapshot traversal includes final membership and metadata rechecks but is not a filesystem transaction. This service requires a quiet workspace controlled by its owner. It does not protect against an adversarial same-user process, privileged concurrent mutation, power loss or a hostile filesystem. After a timeout, interruption or any failure following possible mutation, reconcile the exact source and destination before considering another action; never automatically retry a consumed operation.

## I/O thread lifecycle

Each open root has its own I/O thread, and every native call of that root runs on it, on handles held for the whole operation. One caller thread uses a root at a time. Each call has a deadline: 120 seconds, plus time for flushing a new file at the speed of a slow USB drive (2 MiB per second). A call that does not return in time is cancelled with `CancelSynchronousIo`; after a further five seconds the operation is reported as unresolved (`io-unresolved`) and the root refuses every later call. The bound is best effort: a native call that ignores the cancellation keeps its handles open until it returns. Nothing is retried or resent.

Closing a root stops its thread and closes its handles. While a call is stuck, its handles stay open and are closed as soon as that call returns. There is no background process, named endpoint, socket, daemon or action queue, and no separate shutdown step: close the roots you opened. A timeout or unresolved call keeps the consumed operation unknown until actual receipts and postconditions reconcile it. A valid categorical native refusal remains distinct from an unresolved call.

## Shared Python API and bounds

`ScopedRoot(root, *, quiet_workspace, max_entries=100000)` is a context manager with `inspect`, `list_directory`, `read_bytes`, `create_file`, `move_to` and `remove_file`; `quiet_workspace` must be `True`. It uses the shared `scoped_fs.ScopedFSError` and `CapabilityHold` exceptions. An exact absent leaf reports `missing-entry`; an inaccessible or missing ancestor is a different refusal. Relative paths use `/` and cannot escape the selected root. All content operations take an expected hashed file record.

In-memory reads and exclusive file creation through `ScopedRoot` accept at most 64 MiB. Backups do not use them: they stream each file in 1 MiB pieces through the root's handles, up to 1 TiB per stream. Listings hold at most 100,000 entries and record at most 1,000 "not included" rows, with one final row counting the rest. A nonpositive or excessive bound is refused. The adapter does not silently spill to an unrelated location or weaken verification for a larger file.

`capabilities()` reports what the adapter offers on this computer (64-bit Python on Windows, the NTFS source restriction, the stream and in-memory caps) without opening any selected root. Every actual operation still checks its selected filesystem, sharing, permissions and contents. A positive result is not certification of every volume or permission state.

## Read-only diagnostic recipes

`scripts/diagnostic_windows.py` is the Windows diagnostic adapter. It runs two recipes in Python and starts the fixed helper `scripts/diagnostic_windows.ps1` for the other three, only for an approved real-session diagnostic action, and only as `<system folder>\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -File`, with an environment built from scratch, a 120-second limit and an output bound. Execution policy is never bypassed or changed: under the Restricted or AllSigned policy the helper cannot start and the recipe holds. Dot-sourcing the helper defines functions and collects nothing. Requests and results are unversioned `patchcairn.diagnostics` records with the integer `schema_version` 1.

| Recipe | Bounded evidence | Meaning and limitation |
| --- | --- | --- |
| `windows.os_version` | OS version, build and a fixed architecture category, read in Python | Context for support and compatibility research; does not establish patch completeness. |
| `windows.system_capacity` | Total and available bytes of the drive that holds PatchCairn's work folder, read in Python | A momentary disk-space observation of one drive; other drives are not measured. |
| `windows.update_context` | Up to 50 CBS hotfix KB identifiers and nullable installation dates | An incomplete update context. It does not establish complete history, a pending restart or security remediation. |
| `windows.system_event_metadata` | At most 50 recent selected System events from a fixed provider and event-ID allowlist | Timestamp, numeric ID, numeric level and a public provider name only. |
| `windows.update_event_metadata` | At most 50 recent warning/error/critical events in the WindowsUpdateClient Operational channel | The same metadata projection; no message or event payload is accessed. |

The version recipe uses the running Windows version and `IsWow64Process2`, and the capacity recipe uses `GetDiskFreeSpaceExW`. The update recipe projects only KB identifiers and installation dates from `Get-HotFix`; computer and installer-account fields are not accessed or returned. Event recipes require explicit `window_hours:1` through `window_hours:24` and `max_events:1` through `max_events:50` scope tokens. The System provider allowlist is Kernel-Power, EventLog, WHEA-Logger, disk, Ntfs, Microsoft-Windows-Ntfs and volmgr. The event query also has a fixed ID set. Security/authentication logs, account identifiers, command lines, event messages, event XML and payload properties are excluded.

Results contain typed allowlisted facts, a UTC-Z observation, limitations and official provenance URLs. Unknown fields, executable-looking recipe IDs, broader scope and extra fixture fields are refused. Errors yield categorical holds; raw native error output is not copied into evidence. Fixture mode accepts only injected fictional facts and never invokes a host collector. A separate core API accepts an explicitly selected nonsecret excerpt; this adapter has no arbitrary log-file or command-reading API.

The recipes do not run SFC, CHKDSK repairs, Windows Update scans, resets or servicing commands. The DISM health check and the System File Checker's verify-only mode are listed but hold, because they need an administrator prompt that PatchCairn never opens. Repairs require a concrete separately authorized plan, an account of system-side logs and changes, and their own result verification. No permission barrier is bypassed when a selected event channel is inaccessible.

## Evidence and test limits

`tests/test_windows_io.py` exercises the adapter on fictional NTFS folders under `work/test-fixtures/`: streamed reads and their SHA-256, sharing barriers while a file is read, reparse-point, junction and hard-link refusal, identity changes, the no-replace rename, single-volume moves, removal and its absence check, refused names and path lengths, the backup-destination rules (removable and exFAT/FAT32 drives, the FAT32 4 GiB limit), the deadline that reports a blocked call as unresolved, and root replacement. Conditions that need another volume, a cloud placeholder or a failing native call are faked one call at a time. `tests/Test-WindowsScoped.ps1` runs the diagnostic helper's update and event recipes in fixture mode, its strict request refusals and its script-policy holds; it runs no recipe on the host. Test records state their actual runtime and scope; a fixture pass does not claim a maintenance run occurred.

This page records no test counts, timings or memory measurements. Match suite counts and hosted results to their actual completed source-bound evidence; see [platform evidence](PLATFORM_SUPPORT.md#hosted-fixture-evidence). Neither suite completion nor fixture checks establish general workload speed, other Windows releases/filesystems, cross-volume operations, power-loss recovery or adversarial-concurrency guarantees.

`tests/test_private_workspace.py` and `tests/Test-PrivateWorkspace.ps1` check actual protected Windows directory/file owner/DACL admission and refusal of newly created fictional broad namespaces; the PowerShell suite verifies the ACLs independently through .NET. These tests query only the current process token and owned fictional work objects; they do not inspect another account or change permissions on existing host folders.

## Microsoft API and recipe provenance

These implementation choices follow the documented handle, sharing and metadata interfaces rather than evaluating commands supplied by evidence:

- [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documents sharing rules, directory handles and `FILE_FLAG_OPEN_REPARSE_POINT`.
- [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew) documents canonical handle paths.
- [GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle) documents native identity metadata and filesystem limits.
- [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) and [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) document checked-handle rename, replacement control and disposition permissions.
- [GetDiskFreeSpaceExW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw) and [IsWow64Process2](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-iswow64process2) document the capacity and architecture recipes.
- [Get-HotFix](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-hotfix) documents the QuickFixEngineering/CBS update-history scope.
- [Get-WinEvent](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent) documents `FilterHashtable`, time bounds, levels, providers, IDs, `MaxEvents` and permission limits.
- [CreateDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw), [GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo), [GetTokenInformation](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation) and [ACE inheritance](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules) document the private namespace's creation-time security descriptor, actual owner/DACL readback, token identity and child protection.
