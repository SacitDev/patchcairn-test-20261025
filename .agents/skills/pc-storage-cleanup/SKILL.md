# Storage assessment and cleanup

Read the executing repository's AGENTS.md, the pc-maintenance router and [communication guide](../../../references/COMMUNICATION.md). Then read [the storage workflow](../../../references/STORAGE_CLEANUP_WORKFLOW.md). Use the current `docs/STORAGE_BACKUP_API.md` and workflow engine API before calling helpers; a provisional or missing signature is a capability hold, never a reason to invent flags or substitute a shell deletion.

Operate through chat and the documented helper/CLI adapters; do not operate a storage website or file-manager UI for this workflow. A folder-size chart is a chat explanation. `PatchCairn: start`, `help`, `status`, `options`, `cost`, `settings`, `pause`, `resume`, `stop` and `resolve` are conversation commands routed through the deterministic engine, not host slash commands or shell programs.

## Establish the actual scope

Select the storage job, guided or automatic control, now or scheduled timing, exact owner-chosen roots, exclusions, resource limits and checkpoints. Control and timing are independent. Start with agreed metadata; names and sizes can themselves be private. The owner may choose a device, drives/folders or a problem-focused assessment through the agent workflow. The fixed storage helper still admits only its documented bounded non-volume roots; use available verified read-only observations for broader coverage and label their actual limits. A broad request such as “choose the best cleanup” gives the model discretion to recommend; it does not authorize hashing, backup, moving or deletion.

Keep browser history/cache/profile/session and unrelated private/project content excluded by default. Record exact relevant diagnostic local-read exceptions and separate LLM content selections through the router; never expose credentials/private keys or dump authentication state. The checked cleanup helper's protected roots/names remain ineligible, and a diagnostic exception is not a cleanup grant. Sensitive changes require a separate concrete supported repair plan. Do not follow symlinks, junctions or reparse points, evade access barriers, or infer additional roots from a shortcut or an imported report.

## Explain, choose, review, act

Show metadata results using a compact table and labelled text bars in chat. Report measured logical bytes, excluded/unreadable scope and uncertainty. Do not equate logical size, hardlink names, identical contents or quarantine size with physically reclaimable free space. Additional ordinary-file hashing requires actual, bounded content-read consent before reading bytes. Equal hashes identify duplicate candidates; the owner still chooses which copies serve a purpose.

Offer checkpoints after analysis, after candidate selection, before backup, after backup verification, before deletion and after outcome verification. Honor the selected checkpoints using supported engine gates. Automatic mode can continue under an actual approved exact plan or a valid bounded standing policy that covers the exact current target and action; every concrete plan still needs independent review and fresh checks. Neither settings nor a scheduled trigger replaces human authority. A changed root, target, destination, exclusion, retention decision or material file state needs a fresh concrete plan and actual human binding outside any still-valid narrow policy.

Use one coordinator for state, host mutations and operation receipts. A platform/storage investigator supplies bounded evidence; two distinct independent adversarial reviewers challenge (1) compatibility/data/recovery and (2) evidence/security/scope for every concrete change plan. Missing independent review holds changes while approved read-only work may continue.

Prefer supported same-volume quarantine with a reviewed restoration plan. Required recovery must be verified and protected first. Permanent purge is a separate irreversible plan with an actual explicit loss acknowledgment; quarantine approval never covers it. No generic remove/prune/autoremove, recursive fallback, ACL repair, forced closure, cross-volume copy-delete workaround or unreviewed cloud upload.

Before each action, revalidate exact scope, identity, content, plan hash, capacity, active users, recovery and native capabilities. Pass the engine's action gate, preserve a durable operation receipt, call only the documented fixed helper, and record fresh outcome evidence. Partial, failed or unknown outcomes remain held. Pause prevents new actions immediately; let active work reach a safe checkpoint. Resume reconciles actual state and freshness without replaying a consumed action.

Close with measured results, retained recovery space, unresolved items and a useful next choice. Keep technical IDs and hashes in private owned `work/` records; explain meaning, benefits, drawbacks, costs, reversibility and a recommendation in ordinary language.
